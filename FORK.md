# The Northsky fork of Jetstream

This is `github.com/Ashex/jetstream`, a fork of `github.com/bluesky-social/jetstream`. It adds two
things upstream's v2 server lacks, per the owner's ruling of 2026-11-20 (`appview/06-jetstream.md`, "a live
tail with a rolling window, not an archive"): a **live-only start**, with no full-network bootstrap, and
**window pruning**, which deletes sealed segments older than a window (90 days by default). The wire
protocol, the seq cursors and the archive endpoints stay upstream's, with one declared addition. Upstream's
`CONTRIBUTING.md` asks for an issue before a PR and sign-off on lexicon changes, so the fork carries its own
changes and merges upstream in.

`northsky/appview/data-service/.claude/skills/` has the whole procedure.

`.githooks/pre-commit` runs `just lint`, `just test` and the live-only oracle scenario as its own
invocation; `.githooks/pre-merge-commit` runs the same for a clean merge. Enable once per clone with
`git config core.hooksPath .githooks`. The heavy tiers (`just test-long ./internal/oracle`,
`just oracle-sweep 3`, `just mutation-gate` on a clean tree) run by hand before a tag. Every Go command
needs `GOTOOLCHAIN=go1.27.3` (the hook sets it).

The live-only oracle scenario must run as its own `go test` invocation, because the oracle package has one
synctest bubble and `TestOracle_DefaultLifecycle` claims it when both run (the scenario then skips, and
`just test` hides skips):

```sh
go test ./internal/oracle -run '^TestOracle_LiveOnlyRetention$' -count=1 -v | tee /tmp/lor.log
grep -c -- '--- PASS: TestOracle_LiveOnlyRetention' /tmp/lor.log   # 1
grep -c -- '--- SKIP: TestOracle_LiveOnlyRetention' /tmp/lor.log   # 0
```

## Invariants the fork adds

- A sealed segment is removed only below the durable retention floor, which is committed before any file
  goes. The floor only rises.
- On v2 and the archive endpoints a read below the floor is refused or announced, never skipped, with
  two exceptions: v2 seq cursor, `400 CursorTooOld`; v2 timestamp cursor, `#info OutdatedCursor`;
  `planSnapshot`, `400 CursorTooOld` (checked again after planning, so a prune that lands mid-request is
  refused too); a pruned segment, `404 SegmentNotFound`; a live reader the floor overtakes, an
  `InternalError` frame and then `CursorTooOld` on redial. The exceptions: `listSegments` lists only the
  retained segments, with no signal (upstream's behaviour), and `getSegment` can answer `500` in the
  opener's race between its manifest lookup and `os.Open` (`opener.go:57-68`, upstream's behaviour).
- **v1 `/subscribe` clamps a cursor below the floor silently to it.** That is upstream's frozen v1 contract,
  kept by owner ruling and counted in `cursor_requests_total{mode="clamped"}`.
- **Upstream's "deletion markers retained durably forever" (`docs/README.md:76`) does not hold on the
  fork.** A marker older than the window is pruned with its segment.
- A pruned archive cannot migrate to disaggregated storage (its segment indexes no longer start at 0), and
  disaggregated storage has no pruning.
- A defaulted window prunes only a data dir started live-only or already pruned. A bare `jetstream serve` on
  a fresh data dir refuses; use `--live-only`, or set `--retention-window` explicitly (`0` for upstream's full
  bootstrap and archive).

## Configuration

| Setting | |
|---|---|
| `JETSTREAM_LIVE_ONLY` | Start a fresh data dir at the relay tip. Default false |
| `JETSTREAM_RETENTION_WINDOW` | Default `2160h` (90 days); `0` keeps everything. Local storage only; needs `JETSTREAM_COMPACTION_INTERVAL` above 0 |
| Northsky's deployment | `JETSTREAM_CURSOR_LOOKBACK=2160h` (PD8, so a websocket consumer can resume anywhere in the window); relay `https://bsky.network`, PLC `https://plc.directory` (PD10) |

Metrics: `jetstream_retention_floor_seq`, `jetstream_retention_floor_witnessed_timestamp_seconds`,
`jetstream_retention_window_seconds`, `jetstream_retention_passes_total{result}`,
`jetstream_retention_segments_pruned_total`, `jetstream_retention_bytes_pruned_total`,
`jetstream_subscribe_cursor_requests_total{mode="retention_too_old"}`,
`jetstream_subscribe_disconnects_total{reason="below_retention"}`, `jetstream_plansnapshot_below_retention_total`.
A pruning-stalled alert: `time() - jetstream_retention_floor_witnessed_timestamp_seconds > window + 2 x compaction interval`.

## When upstream changes under a patch

The risky places are cursor resolution (`cursor.go`), the handler's error switches, `ColdReader.Read`, the
compaction loop's `runPass`, `planSnapshot`'s handler, the manifest, the catalog, and anything that reads
`segments/` in the background (it must join `WaitForArchiveLoad`). Keep upstream's side of a conflict and
reapply the fork's few lines. Then rerun `just`, the fork's tests by name
(`go test -short -count=1 ./... -run 'Retention|LiveOnly|RemoveSegment|KeepsEverything'`), the live-only oracle scenario
(its own invocation), `just test-long ./internal/oracle`, `just oracle-sweep 3`, the mutant loop
(`for p in testing/mutation/mutants/*.patch; do git apply --check "$p" 2>/dev/null || echo "STALE $p"; done`
prints nothing; if a mutant goes stale, move the fork's edit, not the mutant) and `just mutation-gate` on a
clean tree.

If upstream ships a retention mode or a live-only start, prefer it and drop ours once the oracle scenario
passes against it.

## Notes

- `retentionCandidates` re-selects a segment at or below the stored floor if a power loss resurrected its
  file; the new floor's `LastIndex` is the larger of the old one and the last candidate's, so the floor stays
  monotonic.
- The crash-point matrix for pruning is the strict-memory power-loss tests
  (`internal/ingest/orchestrator/retention_powerloss_test.go`); the subprocess restart harness drives the
  bootstrap chain and was not extended.
- An interrupted live-only first start leaves `live_only_since` without a phase. A later start without
  `--live-only` refuses ("a live-only start was interrupted; restart with --live-only"), so the marker cannot
  unlock default pruning of a full archive.
- Disaggregated pruning is deferred: it needs catalog transactions, object GC under `GC_DELAY` and follower
  views.
- The `/status` repo verification reports partial repos on a windowed archive.

## Tags and images

The fork versions itself with its own semver, starting at `v1.0.0` (owner, 2026-11-21): a patch release for
fixes, a minor for a new upstream merge or fork feature, a major for a change consumers must act on. Each
release's annotated tag message names the upstream commit it is based on (`v1.0.0`: upstream `c9cbd1b`, after
`v0.4.6`). Upstream's tags are `v0.*` and are never pushed to `origin` (`git push origin main`, then the one new
tag by name; never `--tags`), so no fork tag reuses an upstream name. If upstream ever reaches `v1`, the next
fork release moves to a major above upstream's and this section says so.
`.github/workflows/northsky-image.yml` runs only on tags matching `v[1-9]*.*.*`, only in `Ashex/jetstream`,
refuses to overwrite an existing tag, and pushes `ghcr.io/ashex/jetstream:<tag>` for linux/amd64 from
upstream's unchanged `Dockerfile`. Upstream's `release.yml` is untouched. Pushing the tag and publishing the
image are the owner's.

## Worth asking upstream for

A retention mode (delete sealed segments past a window, with a durable floor every read surface honours)
and a live-only start, as one issue with the oracle scenario; no PR without upstream's sign-off.
